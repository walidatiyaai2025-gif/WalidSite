# وليد سايت — دليل تثبيت باكيدج cPanel

هذه الحزمة تشمل تطبيق Laravel ومكتبات Composer الإنتاجية وملفات public_html والصورة الشخصية المعتمدة. لا تشمل أسرار الخادم أو بيانات قاعدة البيانات أو تطبيقات Flutter. تم إعدادها لرفعها من cPanel File Manager بعد نجاح اختبارات GitHub CI؛ ويظل فحص الاستضافة الفعلية مطلوبًا.

## تنزيل الحزمة والتحقق من سلامتها

اسم الملف الإصدارى هو `WalidSite-Setup-vX.Y.Z.zip`؛ استبدل X.Y.Z بالإصدار الموجود في `application/VERSION` و`PACKAGE-MANIFEST.json` (الإصدار التجريبي الحالي 0.1.2). رفع ملف ZIP الداخلي واحد فقط إلى cPanel؛ وملف `.sha256` للتحقق قبل الرفع وليس خطوة رفع ثانية.

1. افتح صفحة **Actions → PR CI** في GitHub واختر تشغيل **main** الناجح الذي يحتوي على خطوة `build-cpanel-package` بعد نجاح `required-ci-gate` على نفس SHA. نزّل Artifact باسم `WalidSite-Setup-installer` وفك ضغط ملف الـArtifact على جهازك؛ ستجد `WalidSite-Setup-vX.Y.Z.zip` و`WalidSite-Setup-vX.Y.Z.zip.sha256`.
2. تأكد أن الـSHA الظاهر في `PACKAGE-MANIFEST.json` داخل الحزمة يساوي SHA تشغيل GitHub الناجح الذي قمت بتنزيله؛ وجود SHA في ملف بمفرده لا يثبت الهوية أو التوقيع الرقمي.
3. من الطرفية، في نفس مجلد الملفين، نفّذ `sha256sum -c WalidSite-Setup-vX.Y.Z.zip.sha256` (على macOS: `shasum -a 256 -c WalidSite-Setup-vX.Y.Z.zip.sha256`)، ثم `unzip -t WalidSite-Setup-vX.Y.Z.zip` **قبل** استخراج ملفات الاستضافة. عند أي اختلاف أو فقدان لملف checksum لا تستخدم الملف.
4. سكربت البناء يراجع كل ملف داخل ZIP مقابل بصمة SHA256 وحجمه في الـManifest؛ هذه خطوة سلامة للمحتوى، وليست إثبات نشر أو توقيع رسمي. لا تضع ملفات المفاتيح أو `.env` داخل public_html.

## قبل الرفع

1. تأكد أن cPanel يدعم PHP 8.3 أو أحدث وإضافات mbstring و PDO MySQL و openssl و xml و tokenizer و fileinfo و ctype. وفّر HTTPS على الدومين.
2. خذ Backup لأي موقع موجود، وأنشئ قاعدة بيانات MariaDB/MySQL جديدة ومستخدمًا لها من cPanel. احتفظ بالاسم وكلمة السر بعيدًا عن الملفات العامة.
3. ملف ZIP يحتوي على ثلاثة مجلدات رئيسية: application (خاص)، contracts (خاص)، public_html (عام). فك ضغطه من Home Directory للحساب (/home/USERNAME)، وليس من داخل public_html. سيتم دمج public_html مع الجذر العام الحالي؛ راجع أي ملفات متعارضة قبل الكتابة.
4. يجب أن يكون ترتيب الملفات كما يلي:
    /home/USERNAME/application/
    /home/USERNAME/contracts/owner-cv-baseline.json
    /home/USERNAME/public_html/index.php
    /home/USERNAME/public_html/.htaccess

**حماية إضافية محدودة:** تتضمن الحزمة `application/.htaccess` و`contracts/.htaccess` بسياسة منع جميع طلبات HTTP لحماية الملفات الخاصة عند وضعها بطريق الخطأ تحت مجلد عام على Apache/LiteSpeed **إذا كانت صلاحية قراءة `.htaccess` مفعّلة لدى الاستضافة**. هذه الحماية ليست بديلًا عن استخراج ZIP في Home Directory؛ خوادم لا تقرأ `.htaccess` قد تعرض الملفات، ولا تجعل الاستخراج داخل `public_html` آمنًا أو طريقة تثبيت مدعومة. يتم فحص محتوى هذين الملفين ضمن Manifest واختبارات CI.

**شرط مهم:** إذا كان Document Root للدومين ليس `/home/USERNAME/public_html` فطريقة الرفع/الاستخراج مرة واحدة غير مدعومة على ذلك الدومين بالإعداد الحالي. **أوقف التثبيت** واضبط Document Root من واجهة الاستضافة على المسار المدعوم قبل الاستخراج، أو انتظر حزمة مناسبة لجذر الدومين المختلف؛ لا تنقل الملفات يدويًا ولا تعدّل `index.php` أو تضع `application` و`contracts` داخل جذر الويب العام. تأكّد من الجذر الفعلي قبل رفع الملف، فلا توجد هنا آلية لاكتشاف مسار خاطئ بعد استخراجه.

## التثبيت الجديد — من المتصفح فقط دون Terminal أو تحرير .env

1. جهّز **قاعدة بيانات فارغة** واسم مستخدم وكلمة مرور لها من **cPanel → MySQL Databases**. هذه خطوة الاستضافة الوحيدة قبل المعالج؛ الموقع لا يستطيع إنشاء قاعدة MySQL من دون صلاحيات لوحة الاستضافة.
2. فك الباكيدج في **/home/USERNAME**، بحيث تكون application وcontracts خارج public_html. شغّل الدومين باستخدام HTTPS. عند أول تشغيل Laravel **وبشرط عدم وجود APP_KEY مسبقًا**، يولّد المفتاح ورمز التثبيت عشوائيًا في ملف خاص قبل تشغيل معالج الويب؛ لا تحتاج Terminal أو تحرير .env في مسار حزمة cPanel. لا تستبدل مفتاح موقع مُثبّت سابقًا.
3. افتح **https://YOUR-DOMAIN/setup**. داخل cPanel File Manager افتح الملف الخاص **/home/USERNAME/application/storage/app/site-first-run.json** باستخدام **View**، وانسخ قيمة **token** فقط، ثم الصقها في أول خطوة. **لا تنشر هذا الملف أو ترسله إلى أحد**: يحتوي على بيانات تأسيس سرية ومؤقتة بصلاحيات خاصة 0600. يُحذف بعد التفعيل الناجح. وجوده خارج public_html ضروري لمنع زائر غريب من الاستيلاء على الموقع قبل إنشاء حساب المالك؛ لا تنسخ المفتاح الموجود بالملف أو تشارك الملف نفسه.
4. اضغط **Next**: أدخل الحقل الإلزامي **site_url** بعنوان الموقع العام الأساسي بصيغة **HTTPS** مثل `https://example.com` (جذر الدومين فقط، دون مسار أو استعلام أو بيانات اعتماد)، ثم Database Host (عادة localhost)، Port (عادة 3306)، اسم قاعدة البيانات، اسم المستخدم وكلمة المرور. لا يستنتج المعالج APP_URL من ترويسة Host القادمة من الزائر. المعالج **يفحص الاتصال ويتأكد أن قاعدة البيانات فارغة** قبل الحفظ، ثم يحفظ APP_URL وAPP_KEY وبيانات الاتصال في `application/.env` الخاص بصلاحيات **0600** دون عرض كلمة المرور أو تسجيلها في HTTP. 
5. اضغط **Next** لتنفيذ Laravel Migrations الموثوقة الموجودة في النسخة المثبتة، ثم **Next** لتعيين كلمة مرور **مؤكدة بطول 14–128 حرفًا** لحساب المالك من CV الحقيقي المعتمد. بعد النجاح يُنشأ القفل الخاص `application/storage/app/site-installed.lock` ويُعطّل `SITE_SETUP_ENABLED` ويُفرغ `SITE_SETUP_TOKEN` ويُحذف ملف `site-first-run.json`. يُرجع `/setup` عندها 404. كما يمنع حساب مالك نشط في قاعدة البيانات إعادة التثبيت حتى لو فُقد ملف القفل.
6. افتح **/admin/login** وسجّل الدخول. بعد ذلك التحديثات: **/admin/updates**. لا تعطل حماية التخزين أو تنقل application تحت public_html.

إذا لم يظهر ملف `site-first-run.json` في تثبيت **جديد دون APP_KEY**، راجع صلاحيات كتابة `application/storage/app` وتأكد أن PHP 8.3+ وHTTPS يعملان، من دون 777. وجود APP_KEY مسبقًا يمنع التوليد التلقائي عمدًا؛ لا تحذف مفتاح تثبيت قديم. إذا كانت الاستضافة تمنع كتابة application/.env، تظهر رسالة واضحة دون تسريب معلومات الاتصال. لا تُدخل بيانات Production لقاعدة تحتوي بيانات موجودة؛ استخدم قاعدة جديدة وفارغة.

## بعد التثبيت والتحديثات

- لعرض تحديثات قاعدة البيانات افتح /admin/updates بحساب المالك. يمكن تنفيذ migrations الموجودة في نسخة الكود المثبتة، دون أي رفع وتشغيل ملفات PHP مجهولة.
- للتحديثات التلقائية بعد رفع كود جديد موثوق فقط، اضبط SITE_AUTO_MIGRATE=true بعد تجهيز النسخ الاحتياطية وأضف Cron كل دقيقة:
    cd /home/USERNAME/application && /usr/local/bin/php artisan schedule:run >/dev/null 2>&1
  مسار PHP يمكن أن يختلف حسب إعدادات استضافتك.
- فحص Cron الخاص يراقب **الكتالوج الموقّع فقط** ولا ينزّل كودًا أو يطبقه؛ التحميل والتثبيت التلقائيان الكاملان من GitHub Releases لا يزالان غير مُعتمدين. يجب حماية application/.env وبيانات المستخدمين في storage دائمًا.
- لا يتم إنشاء قاعدة البيانات نفسها من واجهة /setup؛ أنشئها أولًا من cPanel. لا توجد بيانات اعتماد مثبتة داخل ZIP. إذا انقطع الاتصال بقاعدة محفوظة **قبل** تفعيل المالك، يمكن إعادة إدخال بيانات قاعدة **فارغة ومتحقق منها** بعد فتح المعالج بالرمز؛ لا يمكن إعادة توجيه قاعدة سليمة أو تجاوز سجل migrations غير المتوافق.


## مراقبة الإصدارات عبر Cron — فحص موقّع وآمن فقط

تتضمن حزمة Setup ZIP **دون أي رفع إضافي** ملفًا خاصًا:
`/home/USERNAME/application/cron/release-poll.php`. هذا الملف **ليس** في `public_html`، ولا يُشغَّل من الويب. لا ينشئ ملف التثبيت الأول مفاتيح الناشر ولا يُفعّل الاستضافة أو Cron نيابةً عن cPanel دون صلاحيات.

**قبل تفعيله:** يجب أن يكون التثبيت مغلقًا، وأن يوافق المالك على أصل HTTPS للناشر ومفتاح Ed25519 العام الأصلي المخزنين في إعدادات الاستضافة الخاصة، مع `SITE_RELEASE_CRON_CHECK_ENABLED=true` بواسطة آلية إعداد موثوقة. قيمة الخيار الافتراضية **false**؛ لا تُفعّل خيارًا أو مفتاحًا مجهولًا. عندما تسمح صلاحيات cPanel API يمكن للمشغّل المعتمد إنشاء Cron مرة واحدة؛ وإلا يتم الإعداد الأول فقط من **cPanel → Cron Jobs**، باستخدام PHP CLI المناسب لاستضافتك، وتعبئة خانة Command (لا حاجة لفتح SSH أو Terminal):

```text
*/15 * * * * /usr/local/bin/php /home/USERNAME/application/cron/release-poll.php >/dev/null 2>&1
```

هذا **مثال**؛ قد يختلف مسار PHP وHome Directory الفعلي. لا تعُدّ Cron نشطًا قبل اختبار الاستضافة المعتمدة. الفحص يقرأ فقط الكتالوج الموقّع، ويكتب النتيجة بصلاحيات 0600 في `application/storage/app/private/release-automation/release-poll-status.json`. إذا كان الإصدار الموقع مساويًا للنسخة المثبتة يعرض `UP_TO_DATE`. إذا كان أحدث، أو فشل التوقيع أو الوصول، تكون الحالة `BLOCKED`؛ **لا يقوم بتنزيل كود جديد أو تغييره** حتى تُستكمل آلية المضيف والتحديث الآمن والفحص الحقيقي والنسخ الاحتياطي والاستعادة. لا يعني `UP_TO_DATE` تحقق تشغيل الدومين أو نشر الموقع.

تظل آلية **التحديث التلقائي الكامل** عبر GitHub Releases، وربط APK بالإصدار المنشور، وإثبات الاسترجاع والـHTTPS الفعلي في Issue #1120 **غير مكتملة**. لا تفعّل التحديثات البرمجية أو تنفيذ migrations اعتمادًا على هذا الفحص وحده.

## النسخ الاحتياطية والاسترجاع قبل أي تحديث

- قبل ترقية الكود احفظ نسخة **مشفرة وآمنة** من قاعدة البيانات والملفات الخاصة، بما فيها مفتاح APP_KEY الأصلي وملفات المستخدمين، خارج public_html. اختبر الاسترجاع على قاعدة بيانات **معزولة**، ثم اختبر التراجع المتوافق عن الكود وقاعدة البيانات معًا، وسجّل SHA النسخة ونتائج الفحص دون تسريب أسرار.
- اترك `SITE_AUTO_MIGRATE=false` حتى يثبت نجاح النسخ والاستعادة والتراجع وCron. تنفيذ `php artisan migrate:rollback` وحده لا يضمن استرجاع البيانات بعد تغييرات مدمرة؛ استخدم خطة ترحيل مرحلية أو استرجاع أمامي عند الضرورة.
- نجاح ملف ZIP أو GitHub CI **ليس نشرًا حقيقيًا**. يتطلب قبول #26 استضافة HTTPS مخوّلة، اختبار أول تثبيت من متصفح حقيقي، إثبات التشغيل ورمز الإصدار، health/queue/cron، واختبار استعادة وRollback موثّقين.

## تحقق سريع

- /up للاستجابة الصحية من إطار Laravel.
- /setup للتثبيت الأول فقط.
- /admin/login لتسجيل الدخول بعد الإعداد.
- /admin/updates لمراجعة migrations بعد دخول المالك.

ملاحظة: نجاح CI يعني صحة بناء الحزمة والاختبارات البرمجية على GitHub؛ لا يعتبر دليلًا على أن استضافتك اكتملت أو أن النشر النهائي T025 قد اجتاز القبول.
