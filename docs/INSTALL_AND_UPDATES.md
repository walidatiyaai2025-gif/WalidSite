# WalidSite first-run setup and trusted updates

**Two supported installation modes; do not combine their secrets or deployment recipes.** The cPanel ZIP ships production Composer dependencies and a browser-only first-run path. A manually prepared Laravel source checkout uses the operator's private `.env` instead. Neither is a public code uploader, database creator, unattended hosting provisioner, or proof of live staging.

## A. cPanel ZIP — automatic browser-only first run (no Terminal)

Package name `WalidSite-Setup-vX.Y.Z.zip` matches the private `application/VERSION` and immutable `PACKAGE-MANIFEST.json.version`. This is a versioned install candidate, not automatically a published production Release.

1. Download the `WalidSite-Setup-installer` artifact from a green **main** CI run for the exact expected commit. Verify its ZIP checksum and `PACKAGE-MANIFEST.json` source SHA. Upload the **single inner `WalidSite-Setup-vX.Y.Z.zip`** to the **cPanel account home** (`/home/USERNAME`) and extract **once there**, not inside `public_html`. This layout requires the site Document Root to be `/home/USERNAME/public_html`; for any other root, STOP before extraction rather than manually moving private files or modifying `index.php`. The archive places sibling private `application/` and `contracts/` outside the public web root and only `public_html/` inside it. The packaged `application/vendor/` is included. Verify PHP 8.3+, Laravel extensions (especially `mbstring`, `pdo_mysql`, `xml`, `openssl`, `fileinfo`) and HTTPS. Both private roots have Apache/LiteSpeed `.htaccess` deny-all guards for defense in depth **only when overrides are honored**; these do not make extraction inside a web root safe, and non-Apache servers may ignore them.
2. In cPanel, **provision a new, empty MariaDB/MySQL database and a least-privileged user**. The wizard does not create or erase a database. Make `application/storage/app`, `application/storage/framework`, `application/bootstrap/cache`, and the private `application/` directory writable by the PHP application user with safe owner permissions; do not use `777` or expose private directories. Back up any existing site before replacing files.
3. On **first Laravel boot without an existing APP_KEY**, `AppServiceProvider::register()` invokes `FirstRunBootstrap::prepare()`. It generates a cryptographically random `APP_KEY` and 64-hex setup token in private `application/storage/app/site-first-run.json` (mode `0600`), and enables setup **in memory**. This file is temporary and must never enter `public_html`, version control, support tickets, URLs, screenshots, or logs. View it privately in cPanel File Manager and copy **only** the `token` value. No manual `php artisan key:generate`, `.env` editing, or `SITE_SETUP_TOKEN` provisioning is required for this packaged flow.
4. Visit `https://YOUR-DOMAIN/setup` using the intended public HTTPS domain. Enter the private token to unlock the session. Supply mandatory **`site_url`** (the canonical **public root HTTPS URL**, e.g. `https://example.com`, without a path, query, fragment, or credentials) plus `db_host`, `db_port`, `db_database`, `db_username`, `db_password`. The site URL is entered by the operator, **never inferred from an untrusted Host header**. The wizard checks the new database's connectivity and emptiness before writing `application/.env` with private `0600` permissions; at that time it persists the generated APP_KEY, validated APP_URL and DB settings. It uses Laravel's `mysql` driver with MariaDB.
5. Run the wizard's **checked-in Laravel migrations**; confirm no incompatible migration history. Activate the existing canonical owner CV identity using a **confirmed 14–128-character password**. Successful activation creates `application/storage/app/site-installed.lock`, disables setup and revokes the saved token, removes `site-first-run.json`, and leaves `/setup` returning 404. A privileged active owner in the database independently blocks reinstall if the lock file is lost. Sign in at `/admin/login`.
6. If saved DB credentials fail **before owner activation**, unlock setup again and provide another **verified empty** database. A healthy existing connection or incompatible migration history is **not** permission to repoint the database. If a previously installed site's APP_KEY is missing, the bootstrap refuses to generate a new one; restore the original private key from a secure backup, never replace it.

**Security boundary:** automatic cryptographic state exists at runtime first; persistent `.env` configuration is created only after a token-authorized, successful empty-DB probe. A browser cannot create cPanel databases, read secrets from the web root, or confirm external email/AI services.

## A.1 Private signed release discovery Cron (Issue #1120; **read-only**)

The same first-install Setup ZIP includes `application/cron/release-poll.php` **outside** `public_html`. It has a CLI-only preflight and cannot run through an HTTP URL. It will refuse uninstalled sites, missing owner lock/private storage, mismatched running VERSION, unknown publisher identity, disabled settings, or a pending maintenance barrier. A private nonblocking lock prevents competing checks; a bounded, owner-only 0600 receipt records `UP_TO_DATE` **only** for a valid Ed25519-signed catalog with the same stable version, or `BLOCKED` for newer/unverified releases. A corrupted/stale receipt is rendered as `UNVERIFIED` in owner Admin → Updates.

**Chained code-only releases:** keep the *same original one-time cPanel Cron command* `HOME/application/cron/release-poll.php`. The launcher holds the existing global shared writer lock, refuses pending maintenance, validates the 0600 private active-release pointer and immutable VERSION lineage, then boots the actual currently served versioned application. The original `.env`, APP_KEY, storage, uploads and owner state remain fixed at `HOME/application`. Corrupt/missing authoritative pointer, unsafe symlinks/permissions, or concurrent exclusive code update fails closed. The selected application only performs signed-catalog discovery; it does **not** apply ZIPs. Verify a real multi-release host update separately before calling this zero-touch deployment.

This is opt-in via server-private `SITE_RELEASE_CRON_CHECK_ENABLED=true`; the shipped default is false. It also requires a verified `SITE_TRUSTED_INSTALLED_VERSION` and the real approved `SITE_TRUSTED_RELEASE_ORIGIN` and `SITE_TRUSTED_RELEASE_PUBLIC_KEY`. Neither the ZIP nor the ChatGPT session supplies keys or invents a domain. The cPanel administrator may add the **single initial** job in cPanel → Cron Jobs (no SSH):

```text
*/15 * * * * /usr/local/bin/php /home/USERNAME/application/cron/release-poll.php >/dev/null 2>&1
```

The exact CLI PHP path and account home must be confirmed by hosting. A scoped authorized cPanel API may configure the job if actually available; otherwise this one-time GUI action is a hosting prerequisite. Cron observation **never** downloads, extracts, installs PHP code, runs migrations or marks a deployment successful. The rest of the unattended verified code update, signed GitHub Release promotion, host adapter/isolated backup/rollback, production APK binding and final live trial remain **OPEN in #1120/#732/#26–#28**. The receipt is local display information, not update authorization.

## B. Manually managed Laravel source checkout (operator/CLI install)

1. Deploy reviewed source with the sibling `contracts/` directory, install Composer dependencies and build frontend assets on your trusted build/hosting environment. Point the server document root to `backend/public`; keep `backend/.env`, storage, contracts and project root private. Supply PHP 8.3+, required extensions and a real HTTPS origin.
2. In a **private** `backend/.env`, set `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL` to the canonical root HTTPS URL, working `DB_CONNECTION=mysql` (MariaDB-compatible) and `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` for an **already-provisioned empty** database; configure `SESSION_DRIVER=file` and `CACHE_STORE=file`. Generate a unique APP_KEY **server-side** using `php artisan key:generate`. Do not reuse CI/test keys. When an APP_KEY already exists, automatic `FirstRunBootstrap` is intentionally skipped.
3. Generate a **separate cryptographically random 32+-character** setup token with an approved secret generator; set `SITE_SETUP_ENABLED=true`, `SITE_SETUP_TOKEN`, and the appropriate initial setup database-ready configuration in the **private** `.env`. Never share the token via query parameters or commit it. Clear/rebuild cached config after private changes.
4. Unlock `/setup` over HTTPS with that token, follow the current database/migration/owner activation steps and check `/admin/login`. When using manually managed setup state, the operator must confirm `SITE_SETUP_ENABLED=false` and clear `SITE_SETUP_TOKEN` in private config after activation; re-cache config. Do not delete or replace the original APP_KEY on upgrades.

**Do not follow path B when using the standard cPanel package's no-Terminal wizard.** An explicit APP_KEY in manual mode suppresses automatic first-run key/token generation.

## Backups, verified recovery, and pre-release checks

Before each upgrade, preserve an encrypted/offsite **consistent database backup and private application/files backup**, including the existing APP_KEY and uploaded data. Restore a copy onto an isolated test database/site, verify data integrity and login/permissions, and rehearse **application artifact + compatible database** rollback. Record tested source SHA, migration inventory, recovery steps and redacted smoke receipts. Do not assume `php artisan migrate:rollback` can reverse destructive schemas or data transformations. Keep `SITE_AUTO_MIGRATE=false` until backup/restore, rollback, scheduler and production-equivalent migrations are tested; phased changes may require forward recovery. Never restore production secrets onto public paths.

A successful cPanel ZIP build or green CI is **not live installation evidence**. T025 requires a genuine authorized HTTPS staging environment, installed release SHA, post-migration health, queue/cron, protected setup endpoints, external integration checks, and real recovery receipts. Use `qa/staging_smoke.py` only with an explicitly approved hostname and controlled network egress; its read-only HTTP observations alone do not attest a deployment or rollback.

## Trusted patch and migration handling

### Admin-signed code-only ZIP updates and local update history

After one-ZIP cPanel installation, the **owner-only Admin → System Updates** page supports **Check publisher → inspect signed version and release notes → Download or upload publisher-approved ZIP → Verify package → Host preflight → Private code staging → Re-enter owner password → Install signed code**. The publisher origin and Ed25519 public key must be explicitly pinned in the **private server configuration**; a SHA-256 checksum alone is not publisher authentication. Signed release notes are bounded and HTML-escaped. Nothing downloaded or staged is executable merely because its signature was verified.

The actual code-only switch is fail-closed: a compatible **physical cPanel** document root, separately authorized `CpanelOwnerCodeUpdateHost` adapter, independently stopped foreign/direct SQL/cron writers, exclusive Laravel writer lease, empty independent MariaDB recovery database, protected file/database snapshot with a verified restore drill, immutable signed ZIP staging and a real independent HTTPS health probe are required. **No default host adapter exists.** If the host cannot prove every gate, the page must show a blocked host instead of attempting a best-effort update. A hosting operator must provision any required capability safely; cPanel GUI can be used without production SSH/Composer/Artisan commands. A code-only ZIP cannot change Composer dependencies or database migration inventory; those require a separately supported migration/deployment path and actual recovery evidence.

A failed candidate health check is never a completed update. For a chained code-only release, the updater can resume the previous release only after its own issued rollback proof independently rechecks the original pointer, full immutable code tree and web entrypoints while the same exclusive writer lease and private maintenance token remain valid. It then removes maintenance so the owner can retry with a newly acquired lease and a fresh independent recovery database. Changed identities, unsafe permissions, expired ownership or unproven recovery keep the maintenance barrier. The disposable ZIP/MariaDB CI rehearsal exercises this failure, resumption and retry; it does not prove real HTTPS hosting or production publisher signing.

On verified completion, the owner page maintains two **different** private histories. **Backup & Recovery** shows historical restore-drill receipts, not proof that an old snapshot remains restorable. **Completed Code Update History** stores a bounded local APP_KEY-MAC-protected receipt (previous/installed SemVer, Git SHA and recovery receipt correlation) *only after* the signed installer reports completed HTTPS health verification and maintenance clearance. An absent/modified/symlinked/unsafe history fails closed and does not display untrusted entries. The local history is neither a publisher signature nor a fresh health check, backup authorization or live staging proof. If its write fails after code cutover, Admin reports **completed installation with an incomplete audit record**, not a false "no update happened" status or unsafe automated rollback.

The separate installed-code migration check remains read-only unless safe, independently proved recovery exists. `SITE_AUTO_MIGRATE` must remain off until backup/restore, database compatibility and the scheduler are verified; automatic cron and live hosting require authorized operations. No cPanel user is expected to run Composer, npm or Artisan during the supported ZIP install/update flow. **The GitHub CI artifacts are inspection/build evidence**, not production signing, physical HTTPS cPanel deployment or owner visual/device acceptance. Issues #732/#26/#27/#28 remain open until those independent tests pass.
